CASE STUDY 01 · FORECASTING & CAUSAL INFERENCE
Causal Demand Forecasting & Promotion ROI

How much of this promotion actually worked?

When sales go up during a promotion, it is easy to give the promotion all the credit. I wanted to know how much of that bump it really caused.

WHAT I BUILTAll of it, from the warehouse to the dashboard
DATAReal daily sales from Favorita, a grocery chain in Ecuador
METHODLightGBM to forecast, OLS to estimate the lift
STACKPython · Snowflake · dbt · Prophet · Streamlit
STORE 44 · GROCERY I · NOVEMBER 2015 PROMOTION
How the 368,070 units break down
TOTAL SOLD368,070
NORMAL DEMAND350,703
FROM THE PROMO17,367 · +5.0%

What I was trying to do

Stores plan stock using forecasts, and they judge a promotion by how much sales went up. The problem is that sales go up for lots of reasons at once, like holidays or payday. If you just compare before and after, the promotion gets credit for sales it did not cause.

So I wanted to answer two things. What will demand look like, and how much did the promotion really add?

What I built

I split it into two parts, because forecasting and measuring a promotion are two different questions.

  • Set up the data in Snowflake and built the dbt models, with tests that catch bad data early.
  • Trained LightGBM to forecast four weeks ahead, tested it 21 times on unseen data, and compared it with Prophet, a moving average and a seasonal baseline.
  • Picked three product groups that moved like GROCERY I before the promotion but were not on promotion themselves (cleaning, dairy and beverages), and used them to estimate what GROCERY I would have sold without it.
  • Put it all in a Streamlit dashboard.

CASE STUDY 02 · EXPERIMENTATION & BI
A/B Test Analytics Framework

Can this experiment be trusted?

I built an A/B testing setup that checks the test is sound before it looks at any results. Then I broke the data on purpose to make sure it would catch the problems.

WHAT I BUILTThe whole thing, from data checks to the dashboard
DATA541,909 real online retail transactions
TEST DESIGNReal transactions, simulated split, with effects I already knew the size of
STACKSQL · DuckDB · Python · Tableau · Streamlit
PROBLEMS I PLANTED IN THE DATA
The checks caught every one before any results were run
LEAKED EVENTS2,000 caught
DUPLICATE ROWS500 caught
IN BOTH GROUPS120 caught

What I was trying to do

Most tutorials jump straight to a t-test. But first you need to know if the test itself is okay. Did users split evenly? Were the two groups similar to begin with? Is data from before the test sneaking in? If any of that is off, the p-value does not mean much.

I had only done pieces of this in coursework, never the whole thing start to finish. So I built all of it.

What I built

  • Cleaned 541,909 transactions down to 397,924, across 4,338 users.
  • Wrote every metric once in SQL, in DuckDB, so both groups are measured exactly the same way.
  • Built checks that run before any results: an even split, no duplicate users, no one in both groups, and no data leaking in from before the test.
  • Ran the tests with a z-test and bootstrap confidence intervals. Conversion was the main metric. I also tracked revenue per user, and order value as a guardrail.
  • Built a Tableau dashboard and a Streamlit app to show the results.

CASE STUDY 03 · GENERATIVE MODELLING
TabDDPM for Hospital Readmission Prediction

Can a diffusion model fix class imbalance in patient data?

We built a diffusion model from scratch to create fake but realistic patient records, and tested whether they could help predict who comes back to the hospital.

WHAT I BUILTThe class conditioning and the pipeline that generates new patients
DATA101,766 diabetic patients from 130 US hospitals
MODELTabDDPM, written from scratch in PyTorch
COMPARED WITHNo augmentation · SMOTE · CTGAN
F1 FOR READMITTED PATIENTS · SAME MODELS, DIFFERENT CUTOFF
Changing the cutoff from 0.50 to 0.15 made F1 about five times better
CUTOFF 0.50F1 ≈ 0.05
CUTOFF 0.15F1 ≈ 0.27

What I was trying to do

Only about 11% of patients in this data came back to the hospital within 30 days. A model trained on that learns to just say "not readmitted" for everyone. It gets 89% accuracy and misses almost every patient who matters.

The idea was to create synthetic readmitted patients and add them to the training data, so the model has more examples to learn from. We wanted to see if a diffusion model did this better than SMOTE and CTGAN.

What I built

I built the part that tells the model which kind of patient to make. It turns the label into a vector the model can use, and passes it in at every one of the 1,000 steps, not just at the start. That way the model does not lose track of it halfway through.

We made synthetic patients at 50%, 100% and 200% of the real readmitted group, then retrained the same XGBoost model on each one, five times over.

Results

MethodF1, readmitted patientsROC-AUC
No augmentation0.05480.6581
SMOTE0.05240.6525
CTGAN0.04800.6599

TabDDPM at 100% had the best ROC-AUC, so it was the best at ranking which patients were most at risk.

Changing the cutoff

All of those used the default cutoff of 0.5. With so few readmitted patients, almost nobody gets a score above 0.5, so the model says "not readmitted" to nearly everyone. We tried ten cutoffs between 0.05 and 0.50, and every method did best at 0.15.

The fake patients looked real. Their distributions matched, and on a t-SNE plot you could not tell them apart from real ones. TabDDPM also gave the same result every run, which SMOTE did not.

CASE STUDY 04 · DEPLOYMENT & CLOUD
YOLOv8 Object Detection on AWS

One EC2 box or managed AWS?

We deployed the same YOLOv8 model two ways on AWS, kept everything else the same, and tested how each one handled changing traffic.

WHAT I BUILTThe YOLOv8 service, its Flask API and the Docker image
COMPAREDOne EC2 server vs ECS Fargate with autoscaling
TESTED ON5,000 COCO images, four traffic levels
STACKPython · Flask · Docker · ECR · ECS · Fargate · CloudWatch
FAILED REQUESTS · QUIET TRAFFIC
ECS Fargate did not drop a request at any traffic level
ONE EC2 SERVER22.3% failed
ECS FARGATE0% failed

What we were trying to do

Object detection needs to stay fast when traffic goes up and down. Most comparisons change a lot of things at once, like the model or the cloud provider, so you cannot tell what made the difference.

We changed only one thing: how it was deployed. Same model, same Docker image, same images, same traffic. One version ran on a single EC2 server. The other ran on ECS Fargate with a load balancer and autoscaling.

What I built

I set up the YOLOv8 model, wrapped it in a small Flask API and packaged it with Docker into ECR. You send it an image, it runs detection and sends back what it found. The model loads once when the service starts, not on every request.

Both setups pulled this same image, so any difference came from the deployment and not the code. We tested four traffic levels, from quiet to high, and tracked response time, failed requests and resource use.
